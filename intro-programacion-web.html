Lenguajes Compilar vs Transpilar Descriptivo vs Imperativo DOM

¿Qué es un lenguaje de programación?

Un lenguaje de programación es un sistema formal que permite darle instrucciones a una computadora. Para que esas instrucciones sean válidas tienen que respetar una sintaxis (reglas de escritura) y una semántica (significado de lo escrito).

Pero no todo lo que parece un lenguaje lo es. Hay una distinción importante:

TérminoQué esEjemplo
Lenguaje de programaciónTiene lógica, variables, control de flujo, puede computar cualquier cosaPython, JavaScript, TypeScript
Lenguaje de marcadoDescribe estructura o formato, no tiene lógicaHTML, XML, Markdown
Lenguaje de estilosDescribe presentación visual, no tiene lógica (en su forma básica)CSS
LibreríaCódigo reutilizable que extiende un lenguajeReact (extiende JS)
FrameworkEstructura completa que dicta cómo organizar tu appNext.js, Angular
Extensión de sintaxisAgrega nueva sintaxis a un lenguaje existente, se transpila al originalJSX, TypeScript
La pregunta clave
¿Puede este lenguaje tomar una decisión (if/else), repetir algo (loop) y guardar datos (variable)? Si sí, es un lenguaje de programación. HTML y CSS no pueden — solo describen.

Compilar vs Transpilar vs Interpretar

Tres formas distintas de convertir código que escribís en algo que la máquina puede ejecutar:

ProcesoQué haceResultadoEjemplo
CompilarConvierte código a lenguaje de máquina (binario)Archivo ejecutable (.exe, binario)C, C++, Rust
TranspilarConvierte código a otro lenguaje de similar nivelCódigo fuente legible en otro lenguajeTypeScript → JS, JSX → JS
InterpretarEjecuta el código línea por línea en tiempo realNinguno — corre directoPython, JS en el browser
Python — interpretado

El intérprete lee y ejecuta cada línea en el momento. No hay paso previo. Los errores aparecen cuando esa línea se ejecuta.

python app.py
# corre directo, sin paso previo
TypeScript — transpilado

Primero se transpila a JavaScript. Los errores de tipos aparecen en el editor, antes de correr.

tsc app.tsx → app.js
node app.js # o el browser

El DOM — qué es y por qué importa

Cuando el browser carga una página HTML, no lo lee como texto plano. Lo convierte en un árbol de objetos en memoria llamado DOM (Document Object Model). Cada etiqueta HTML se convierte en un nodo del árbol que podés leer y modificar con JavaScript.

// El HTML que escribís
<body>
  <p id="contador">0</p>
  <button>Agregar</button>
</body>

// El árbol que el browser construye en memoria
document
└── body
    ├── p#contador  → texto: "0"
    └── button      → texto: "Agregar"

// Cómo lo modificás con JS
document.getElementById('contador').innerText = '1'
// modificás el nodo en memoria → el browser re-dibuja esa parte
El problema del DOM manual
En una app grande con muchos componentes compartiendo datos, vos eras responsable de actualizar cada nodo del DOM manualmente. Si te olvidabas uno, la pantalla mostraba datos desactualizados. React resuelve esto automatizando ese proceso.

Diferencia clave — orden de ejecución

Esta fue una de las dudas más importantes de la sesión. Python es estrictamente secuencial. JavaScript tiene hoisting:

# saludar no existe todavía

    return "hola"
JavaScript — hoisting
saludar()  // ✅ funciona
// JS pre-escanea las funciones declaradas

function saludar() {
  return "hola"
}

// Arrow functions NO tienen hoisting
const saludar2 = () => "hola"  // no se iza

HTML, CSS y JavaScript

Las tres tecnologías base de la web. Qué hace cada una, dónde corre, y cómo se relacionan en una página real.

Los tres roles

HTML — Estructura
Define qué elementos existen y en qué orden. No tiene lógica. Es un lenguaje de marcado, no de programación.
CSS — Presentación
Define cómo se ve cada elemento. Colores, tamaños, posición, animaciones. Tampoco es un lenguaje de programación en su forma básica.
JavaScript — Comportamiento
El único lenguaje de programación que corre nativo en el browser. Agrega lógica, eventos y manipulación del DOM.
JSX / TSX — Componentes
Extensión de sintaxis de JS. Mezcla estructura y lógica en un solo lugar. Se transpila a JS antes de llegar al browser.

El problema de Vanilla JS — el ejemplo del carrito

Antes de React, si querías un carrito de compras tenías que actualizar el DOM manualmente en cada cambio:

// EL ESTADO — datos en crudo
let items = ['Pan', 'Leche']

// LA VISTA — función que dibuja según los datos
function render() {
  document.getElementById('contador').innerText = items.length

  const lista = document.getElementById('lista')
  lista.innerHTML = ''  // borramos todo y redibujamos

  items.forEach(item => {
    const li = document.createElement('li')
    li.innerText = item
    lista.appendChild(li)
  })
}

// EL EVENTO
document.getElementById('btn').addEventListener('click', () => {
  items.push('Manzana')
  render()  // ← tenés que acordarte siempre
})

render()  // primer render: muestra el estado inicial antes de cualquier click
Por qué el primer render
Sin él, el usuario ve una página en blanco hasta que clickea algo. El primer render muestra el estado inicial — aunque sea vacío, es el punto de partida correcto.

Esto funciona, pero vos sos responsable de llamar render() cada vez. En una app con 50 eventos distintos, es fácil olvidarse de uno y que la pantalla quede desactualizada.

La solución de React

React dice: la pantalla ES una función de los datos. Si los datos cambian, React recalcula la pantalla. Vos no tocás el DOM nunca.

re-renderiza

React y JSX

Qué es React, por qué se inventó, qué es JSX, y las reglas de sintaxis que necesitás para leer código.

Qué es React — y qué no es

React es una librería de JavaScript creada por Facebook en 2011 y publicada en 2013. No es un lenguaje ni un framework completo. Se encarga de una sola cosa: mantener la interfaz sincronizada con los datos.

El problema original — Facebook 2011
El contador de notificaciones aparecía en la barra superior, en el chat y en el ícono de la pestaña. Todos mostraban números distintos porque cada parte del código actualizaba su propio DOM de forma independiente. Los datos y la pantalla se desincronizaban constantemente.

JSX — JavaScript XML

JSX son las siglas de JavaScript XML. Se llama XML porque la sintaxis de etiquetas <p>, <div> viene del mundo XML/HTML. No es un lenguaje nuevo — es una extensión de sintaxis que se transpila a llamadas de función:

JSX — lo que escribís
const elemento = <p>Hola mundo</p>
JS — lo que el browser ejecuta
const elemento = React.createElement(
  'p', null, 'Hola mundo'
)

Los dos modos dentro de un archivo .tsx

// MODO JAVASCRIPT — definís variables, lógica, funciones
const App = () => {
  const nombre = "Juan"
  const items = ["Pan", "Leche"]

  // MODO JSX — describís la estructura visual
  return (
    <div>
      <p>{nombre}</p>   // {} abre ventana de vuelta a JS
    </div>
  )
}

// Regla: fuera del return → JS  |  dentro del return → JSX  |  dentro de {} → JS

Extensiones de archivo

ExtensiónContenidoCuándo se usa
.jsJavaScript puroSin tipos, sin JSX
.jsxJavaScript + JSXReact sin TypeScript
.tsTypeScript puroCon tipos, sin JSX
.tsxTypeScript + JSXReact con TypeScript — lo más común

Reglas de JSX

1 — Todo debe cerrarse

<input />        // ✅ self-closing
<input>          // ❌ en JSX es error
<div></div>      // ✅ apertura y cierre

2 — Solo una raíz por return

// ❌ dos raíces
return (
  <h1>Título</h1>
  <p>Texto</p>
)

// ✅ Fragment — no agrega nada al DOM
return (
  <>
    <h1>Título</h1>
    <p>Texto</p>
  </>
)

3 — className, no class

<div className="caja">    // ✅ JSX
<div class="caja">         // ❌ class es reservado en JS

4 — style recibe objeto, no string

// ❌ HTML
<p style="color:red; font-size:20px">

// ✅ JSX — objeto JS, camelCase
<p style={{ color: 'red', fontSize: '20px' }}>
//        ↑↑ doble llave: la exterior abre JS, la interior es el objeto

5 — Listas con map y key

const items = ["Pan", "Leche", "Manzana"]

return (
  <ul>
    {items.map(item => (
      <li key={item}>{item}</li>
      //  ↑ key es obligatorio — le dice a React qué elemento es cuál
    ))}
  </ul>
)

6 — Condicionales

// Ternario — mostrar uno u otro
{logueado ? <p>Bienvenido</p> : <p>Iniciá sesión</p>}

// && — mostrar solo si es true
{tieneError && <p style={{ color: 'red' }}>Error</p>}

Estado — useState

Cómo React detecta cambios y actualiza la pantalla automáticamente. El concepto más central de React.

El problema — React no ve tus variables

// ❌ React no sabe que esto cambió
let items = []
items.push('Manzana')
// la pantalla no se actualiza

// ✅ React sí lo detecta
const [items, setItems] = useState([])
setItems([...items, 'Manzana'])
// React detecta el cambio → re-renderiza → pantalla actualizada

La sintaxis desglosada

const [items, setItems] = useState<string[]>([])
//    │       │             │               │
//    │       │             │               └─ valor inicial
//    │       │             └─ tipo TypeScript: array de strings
//    │       └─ función para cambiar el valor — siempre se llama set + Nombre
//    └─ el valor actual — lo usás para mostrar en pantalla

// useState devuelve un array con dos cosas:
// resultado = [ valorActual, funciónParaCambiar ]
// el destructuring [items, setItems] extrae las dos

Por qué const si el valor cambia

No estás mutando el const. React re-ejecuta el componente completo con un valor nuevo en cada render. En cada ejecución, el const recibe el valor actualizado que React guardó internamente.

// Render 1 — items = []
const [items, setItems] = useState([])

// Usuario clickea → setItems(['Manzana'])

// Render 2 — React re-ejecuta el componente
const [items, setItems] = useState([])
// items = ['Manzana']  ← React recuerda el último valor
// el valor inicial [] se ignora en re-renders

Por qué spread y no push

// ❌ Muta el array original — React ve el mismo objeto → no re-renderiza
items.push('Manzana')
setItems(items)

// ✅ Crea un array NUEVO — React ve un objeto diferente → re-renderiza
setItems([...items, 'Manzana'])

// Lo mismo con objetos
setUsuario({ ...usuario, edad: 30 })  // ✅ objeto nuevo
setUsuario({ edad: 30 })               // ❌ pisa nombre y todo lo demás

useState con distintos tipos

useState<number>(0)
useState<string>('')
useState<boolean>(false)
useState<string[]>([])
useState<Usuario | null>(null)

// Con interface para tipar objetos complejos
interface Usuario {
  nombre: string
  edad: number
}
useState<Usuario[]>([])

Props — pasar datos entre componentes

Cuando dos componentes necesitan los mismos datos, el estado sube al padre y los datos bajan como props.

// Interface — define la forma de las props
interface TiendaProps {
  items: string[]
  setItems: (x: string[]) => void
  //         ↑              ↑
  //    tipo del arg    no retorna nada (void = None en Python)
}

// Componente — recibe las props
const Tienda = ({ items, setItems }: TiendaProps) => {
//              ↑ destructuring    ↑ tipo
  return (
    <button onClick={() => setItems([...items, 'Manzana'])}>
      Agregar
    </button>
  )
}

// Uso — padre pasa los datos
<Tienda items={items} setItems={setItems} />
// los nombres deben coincidir con los de la interface
Prop drilling — el problema
Si muchos componentes necesitan los mismos datos y están muy anidados, tenés que pasar las props por cada nivel aunque no las usen. Eso se llama prop drilling y es exactamente el problema que resuelve Context.

Context — compartir datos sin props

Cómo crear un canal de datos que cualquier componente del árbol puede consumir directamente, sin pasar props por cada nivel.

El problema visual

// Sin Context — prop drilling
App → Seccion → Contenido → Fila → Navbar
// items tiene que pasar por Seccion, Contenido y Fila
// aunque ninguno de los tres lo use

// Con Context — acceso directo
CarritoContext ————————————————→ Navbar
// Navbar se conecta directo al canal, nadie del medio sabe que existe

Los 4 pasos — siempre son los mismos

Paso 1 — Crear el canal

// La interface define qué datos va a compartir el contexto
interface CarritoContextType {
  items: string[]
  agregar: (item: string) => void
}

// createContext crea el canal con valores por defecto
// estos defaults solo se usan si no hay Provider encima
const CarritoContext = createContext<CarritoContextType>({
  items: [],
  agregar: () => {},  // función vacía como placeholder
})

Paso 2 — El Provider

export const CarritoProvider = ({ children }: { children: React.ReactNode }) => {
//                               ↑
//             children es reservado — React lo llena con lo que ponés adentro

  const [items, setItems] = useState<string[]>([])

  const agregar = (item: string) => {
    setItems([...items, item])
  }

  return (
    <CarritoContext.Provider value={{ items, agregar }}>
    //                        ↑
    //              lo que ponés disponible para todos los hijos
      {children}
      //  ↑ acá se renderizan los componentes que envuelve el Provider
    </CarritoContext.Provider>
  )
}

Paso 3 — Envolver

// Podés envolver toda la app
<CarritoProvider>
  <App />
</CarritoProvider>

// O solo una sección — solo esa parte tiene acceso
const App = () => (
  <div>
    <Header />              // ❌ no tiene acceso
    <CarritoProvider>
      <Tienda />            // ✅ tiene acceso
      <Navbar />            // ✅ tiene acceso
    </CarritoProvider>
    <Footer />              // ❌ no tiene acceso
  </div>
)

Paso 4 — Consumir

// Hook personalizado — el atajo
export const useCarrito = () => useContext(CarritoContext)

// En cualquier componente hijo
const Navbar = () => {
  const { items } = useCarrito()     // solo pedís lo que necesitás
  return <p>{items.length} items</p>
}

const Tienda = () => {
  const { items, agregar } = useCarrito()
  return (
    <button onClick={() => agregar('Manzana')}>
      Agregar
    </button>
  )
}

Efectos — useEffect

Cómo ejecutar código fuera del ciclo de render — APIs, suscripciones, timers — y cuándo limpiarlo.

El problema que resuelve

En React, todo el código del componente corre en cada re-render. Pero hay cosas que no querés que corran siempre — una llamada a la API, una suscripción, un timer. useEffect te da control sobre cuándo corre ese código.

const Componente = () => {
  // ❌ Esto correría en CADA render — crearía muchas suscripciones
  supabase.auth.onAuthStateChange(...)

  // ✅ Esto corre solo una vez — una sola suscripción
  useEffect(() => {
    supabase.auth.onAuthStateChange(...)
  }, [])

  return <div>...</div>
}

Las tres formas

// FORMA 1 — corre en cada render (casi nunca se usa)
useEffect(() => {
  console.log('corro siempre')
})

// FORMA 2 — corre una sola vez al montar
useEffect(() => {
  console.log('corro una vez')
}, [])  // ← array vacío

// FORMA 3 — corre cuando cambia algo específico
useEffect(() => {
  console.log('corro cuando usuario cambia')
}, [usuario])  // ← array de dependencias

El array de dependencias

La regla es: poné en el array todo lo que usás dentro del efecto y que puede cambiar entre renders.

// Usás nombre adentro → va en el array
useEffect(() => {
  document.title = `Hola ${nombre}`  // usa nombre
}, [nombre])                              // va en el array

// No usás nada que cambie → array vacío
useEffect(() => {
  fetch('/api/config').then(...)   // no depende de ningún estado
}, [])

// Error común — usás algo pero no lo ponés
useEffect(() => {
  console.log(items)  // usa items
}, [])              // ❌ items siempre va a ser [] adentro del efecto

La limpieza — el return

useEffect(() => {
  // SETUP — corre al montar o cuando cambia la dependencia
  const intervalo = setInterval(() => {
    console.log('tick')
  }, 1000)

  // CLEANUP — corre antes de desmontarse
  // sin esto el timer seguiría corriendo aunque el componente no exista
  return () => clearInterval(intervalo)
}, [])

El ciclo de vida completo

// 1. Componente aparece (mount)
//    → corre el código del useEffect

// 2. Dependencia cambia
//    → corre el return (cleanup del efecto anterior)
//    → corre el código del useEffect de nuevo

// 3. Componente desaparece (unmount)
//    → corre el return (cleanup final)

Cierre — el código de auth completo

Ahora podés leer el código original que arrancó toda esta sesión y entender cada línea:

export const AuthProvider = ({ children }: { children: React.ReactNode }) => {

  // Tres variables de estado — un Provider puede tener muchas
  const [session, setSession] = useState<Session | null>(null)
  const [user, setUser]       = useState<User | null>(null)
  const [loading, setLoading] = useState(true)

  useEffect(() => {

    // PARTE 1 — verificar si ya hay sesión activa al arrancar
    supabase.auth.getSession().then(({ data: { session } }) => {
      setSession(session)
      setUser(session?.user ?? null)  // optional chaining + nullish coalescing
      setLoading(false)
    })

    // PARTE 2 — escuchar cambios futuros (login, logout, token renewal)
    const { data: { subscription } } = supabase.auth.onAuthStateChange(
      (_event, session) => {   // _event con _ = "llega pero no lo uso"
        setSession(session)
        setUser(session?.user ?? null)
        setLoading(false)
      }
    )

    // PARTE 3 — cleanup: cancelar la suscripción cuando el componente muere
    return () => subscription.unsubscribe()

  }, [])  // array vacío — corre una sola vez al montar

  // Pone los tres estados disponibles para toda la app
  return (
    <AuthContext.Provider value={{ session, user, loading }}>
      {children}
    </AuthContext.Provider>
  )
}

// El atajo para consumir en cualquier componente
export const useAuth = () => useContext(AuthContext)
